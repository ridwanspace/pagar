# Step 01: Discovery & the documentation plan

## Step goal

Decide **WHO the guide serves, HOW it is organized, and WHAT gets written first, WITH THE USER,
before touching any file.**

## Mandatory rules

- 🛑 **Nothing is created or written until the user approves.**
- 📖 Read this whole step before acting.

## Sequence

### 1. Ground yourself first: read, do not ask what you can read

The requirements, the shipped surface from the machine-readable contract, and any existing
documentation. **Arrive at the interview informed.**

### 2. Interview, one topic at a time, with options and a recommendation

1. **Audience.** Who reads this, and at what level?
2. **Organization.** Three options, **with a recommendation:**
   - **Flat**: about eight pages or fewer, one audience. **The default for small surfaces.**
   - **By feature area.**
   - **By audience.** ⚠ **Costs more structure. Recommend it ONLY when the audiences genuinely
     diverge.**
3. **Copy language**, per the locked decisions.
4. **Scope.** Which surfaces are in the guide's contract? ⚠ **This choice makes every surface in
   scope MANDATORY to document, and every documented surface MANDATORY to exist. That two-way rule
   is what the parity guard enforces.**
5. **The shape of the API reference.**
6. **The first pages.** Propose **three to six** from work that is actually DONE. **Always include
   an index or landing page, and the getting-started page every project has.**

### 3. Concept-versus-mechanical triage

For each proposed page, decide whether it needs a mental model before the steps.

**One-line test:** *if understanding adds nothing beyond the steps, SKIP the model.*

### 4. The documentation plan: the approval gate

Present a plan of **fifteen lines or fewer**, then:

> ⏸️ **[A] Approve and scaffold · [E] Edit the plan · [X] Stop here**

🛑 **Nothing is created until [A].**

Then load `steps/step-02-scaffold.md`.
