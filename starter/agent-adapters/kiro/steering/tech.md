## Configuration

- Configuration comes from the environment. Read it once at startup into a typed object, not
  scattered `getenv` calls at the point of use.
- Secrets are environment variables. Never a literal in source, never in a committed config file,
  never in a test fixture.
- Anything prefixed for the client bundle is public. A build-time variable that ships to the
  browser is readable by anyone who opens devtools. Never put a secret behind one.
- A missing required variable fails loudly at startup. It does not default to something plausible
  and fail confusingly three hours later.

- A new dependency needs a stated reason. It is a permanent cost paid by everyone who builds,

- Prefer the standard library for anything small. A one-function dependency is not worth a supply

## Performance and reliability constraints

These are the ones that cause production incidents, so they get named rather than assumed.

- **Every list endpoint is paginated.** No exceptions, no "this table is small". Tables grow.
- **No N+1 queries.** When you loop over rows and query inside the loop, you have written one.
  Load the related data in one query.
- **Every outbound call has a timeout.** A call with no timeout is a hang waiting for the worst
  day of the year.
- **Retries are bounded and backed off.** Unbounded retry against a struggling service is how a
  degradation becomes an outage.
- **Anything that can be delivered twice must be safe to apply twice.** Use an idempotency key
  for operations that create or charge.

## Schema changes

- A model change and its migration ship together, in the same change. A model change without a
  migration is a broken deploy waiting for the next restart.
- Never create a column and make it NOT NULL in one deploy. Expand, backfill, contract, as three
  separate steps.
- {{MIGRATION_TOOL_AND_CONVENTION, e.g. "Alembic revisions in migrations/versions/, generated
  with alembic revision --autogenerate, always reviewed by hand before commit"}}
- An autogenerated migration is a draft. Read it. Autogeneration regularly gets drops and renames
  wrong, and a wrong migration is the one class of bug that a test suite cannot catch before it
  runs in production.

## API compatibility

- Adding an optional field is safe. Removing a field, renaming one, or narrowing a type is a
  breaking change even when every test passes.
- A behavior change silently invalidates the documentation that described the old behavior. When
  you change behavior, grep the docs and the schema descriptions for what you changed.

## Observability

- Structured logging, not print. {{LOGGING_LIBRARY_AND_FORMAT}}
- Never log a secret, a token, a password, or a full request body that might carry one.
