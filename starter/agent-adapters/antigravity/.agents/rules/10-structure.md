## Layering

{{LAYERING_RULE, e.g. "api calls services, services call models, and nothing calls upward."}}

- A lower layer never imports from a higher one. If a model needs something from a service, the
  design is wrong, not the import.
- Business logic lives in the service layer. A request handler containing a decision is a handler
  you cannot test without a web server.

A layering violation is a design bug, not a style preference. Raise it rather than working around
it.

## Change discipline

- Change the minimum that makes the task correct.
- A refactor is its own change with its own reason. Mixing a refactor into a feature makes the
  feature unreviewable, because nobody can tell which lines carry the behavior change.
- Match the file you are in. If a pattern is genuinely bad, raise it as a decision. Fixing it
  silently in one file leaves the codebase with two patterns instead of one.
- {{READ_ONLY_PATHS, e.g. "legacy/ is reference only, never modify it"}}

## Schema changes

- A model change and its migration ship together, in the same change. A model change without a
  migration is a broken deploy waiting for the next restart.
- Never create a column and make it NOT NULL in one deploy. Expand, backfill, contract, as three
  separate steps.
- {{MIGRATION_TOOL_AND_CONVENTION}}
- An autogenerated migration is a draft. Read it. Autogeneration regularly gets drops and renames
  wrong, and that is the one class of bug a test suite cannot catch before production.

## Reliability constraints

Named rather than assumed, because these are the ones that cause incidents.

- **Every list endpoint is paginated.** No exceptions, no "this table is small". Tables grow.
- **No N+1 queries.** Looping over rows and querying inside the loop is one. Load related data in
  one query.
- **Every outbound call has a timeout.** A call with no timeout is a hang waiting for the worst
  day of the year.
- **Retries are bounded and backed off.** Unbounded retry against a struggling service turns a
  degradation into an outage.
- **Anything deliverable twice must be safe to apply twice.** Use an idempotency key for
  operations that create or charge.

## API compatibility

- Adding an optional field is safe. Removing one, renaming one, or narrowing a type is breaking,
  even when every test passes.
- A behavior change silently invalidates the documentation that described the old behavior. When
  you change behavior, grep the docs and the schema descriptions for what you changed.

## Documentation lives in two homes

- **Working notes** stay next to the workflow: specs, story files, review notes, recorded lessons.
- **Team-facing documentation** lives under `docs/`, committed for everyone, carrying no
  references to private workflow files, no internal spec IDs, no machine-local paths.

When a change makes a fact wrong, fix it in both homes in the same change. A committed page that
contradicts the code is worse than no page, because people trust it.
